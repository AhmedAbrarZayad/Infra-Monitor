1 · Introduction: the ideas to explain

Software and software engineering

Software includes executable instructions, the data structures they use, and descriptive information such as operating and user documentation. It can be a product or a vehicle that controls devices and delivers other products.

Software engineering applies a systematic, disciplined, measurable approach to software development, operation, and maintenance.

Layered technology

Quality focus supports process, which organizes the work; methods describe technical how-to; tools automate or assist the process and methods.

Memory line: quality → process → methods → tools. Tools do not replace a suitable process or engineering judgement.

Why software needs engineering

  • Complex systems need deliberate requirements and design.
  • Failures can affect service availability, security, and trust.
  • Users and technology change, so successful software must be maintainable.

Key contrast: software does not physically wear out like hardware; changes can introduce defects, so it may deteriorate unless maintained carefully.

Apply it to this project

  • Problem: fragmented, reactive Linux-server monitoring.
  • Goals: enrollment, metric visibility, anomaly detection, incident workflow, Request Shield, role-based tenant access, repeatable deployment.
  • Quality concerns: correct organization isolation, reliable telemetry, security, maintainability, and usable investigation workflows.
Likely descriptive prompt: “Define software engineering and explain its importance to Infra Monitor.” Include the definition, layered technology, project problem, quality risks, and how systematic requirements/design/testing reduce those risks.

2 · Process model: Agile/Scrum in the project

A software process is an adapted framework of activities, actions, tasks, work products, and checks for building and evolving software. A process creates control; it should fit the product, team, and risks rather than become paperwork for its own sake.

Generic framework activities

Communication → Planning → Modeling → Construction → Deployment

Umbrella work continues across activities: project tracking, risk management, quality assurance, configuration management, and technical reviews.

Why this team used Scrum

  • Seven two-week sprints across a 14-week project.
  • Each sprint aimed to produce an integrated, reviewable increment.
  • Short feedback cycles helped expose integration and requirement issues sooner than a single end-of-project delivery.
  • Scale was appropriate for a three-person academic team; full microservice decomposition was avoided.

Project increments (high-level)

Compare models in one sentence

Waterfall: sequential; suitable for stable requirements, but late feedback is risky. Prototyping: clarifies uncertain requirements or interfaces. Spiral: iterative with explicit risk analysis; useful for large, high-risk work. Unified Process: use-case driven, architecture-centric, iterative and incremental.

Strong exam response

Name the model; draw the cycle; give project cadence and a concrete sprint example; justify the fit; contrast one alternative and its trade-off. Do not claim Scrum eliminates planning or documentation.

Remember: a model organizes work; it does not guarantee a good product by itself.02

3 · Architectural design: the system-level view

Architecture describes major elements, their responsibilities, and the connections that let them meet system-level goals. Infra Monitor uses a hybrid: client–server + layered backend + selected ML microservice.

Diagram B · Simplified architecture — follow arrows; solid lines are primary calls/data paths.

Why this hybrid fits

  • Client–server gives the Flutter app a clear API boundary.
  • Domain-separated Django apps keep related rules together.
  • Separate ML inference isolates compute and permits independent model-service deployment.
  • Celery/Redis moves scheduled or long-running work away from interactive requests.

Trade-offs to mention

A microservice adds network, deployment, and failure boundaries, so only ML workloads are separated. A pure monolith could blur domain boundaries; splitting every domain into a service would add more coordination than this small team needed.

Likely descriptive prompt: “Draw and explain Infra Monitor’s architecture.” Label client, backend, worker/broker, databases, ML service, and external APIs; explain one request path and one telemetry/anomaly path; finish with rationale and a trade-off.
Data stores: PostgreSQL for application records; VictoriaMetrics for time-series telemetry.03
04 · COMPONENT DESIGNINFRA MONITOR QUIZ REVIEW

4 · Component design: responsibilities and interfaces

Component design decomposes the architecture into cohesive modules. A good explanation says what each component owns, what it accepts/returns, and which dependency it uses. Keep presentation, domain rules, persistence, and external integrations distinguishable.

Diagram C · Component boundaries — boxes are logical components; arrows identify the collaboration direction.

Example contracts

  • Enrollment: authorized organization request → enrollment/configuration response.
  • Telemetry: agent remote-write → accepted metric series; backend/worker queries a time window.
  • Anomaly: feature window → score/confidence → persisted detection; qualifying anomaly can create/update an alert.
  • Shield: request features → GREEN/GRAY/RED + confidence → stored log and possible suggestion.

Patterns named in the report

  • Strategy: select classifier route (ML, rule, or Gemini) by configuration/zone.
  • Factory: create short-lived one-use WebSocket tickets.
  • Observer-like scheduling: periodic Celery events trigger background jobs.
  • Facade: shared helpers hide recurring membership/pagination details.

Explain the responsibility and benefit; do not identify a pattern solely by its name.

Two project flows worth practising

Metrics → anomaly: Linux host/Alloy → telemetry gateway → VictoriaMetrics → scheduled Celery task queries a window → FastAPI Isolation Forest → detection callback → Django stores detection and may create/update an alert → client displays it.
Request Shield: access log → normalize/extract 26 features → scheduled batch (up to 500 records) → Random Forest returns zone/confidence → Django persists result → threshold may create a threat suggestion; gray cases may be escalated to Gemini when configured.

6 · Testing: strategy, levels, and techniques

Verification vs validation

Verification: “Are we building the product right?” Check the implementation against its design/specification.

Validation: “Are we building the right product?” Check that the product meets user needs and requirements.

Testing is not debugging

Testing runs planned checks to reveal failures and provide evidence. Debugging investigates a failure’s cause and fixes it. Testing can reveal defects; it cannot prove the absence of all defects.

Diagram E · Incremental testing, small to large

White-box / structural

Uses internal code/control structure: exercise statements and independent paths, both outcomes of decisions, loops at boundaries, and important data flows.

Cyclomatic complexity: V(G) = E − N + 2, or P + 1 for a connected flow graph; it estimates the number of independent paths to consider, not correctness.

Black-box / behavioral

Checks externally visible behavior against requirements without relying on internal implementation. Look for missing/incorrect functions, interface/data errors, performance and start/stop behavior.

High-yield test design techniques

TechniqueIdeaProject example
Equivalence partitioningChoose representatives from valid and invalid input classes.Valid login vs wrong password; duplicate email vs unique email.

Unit-test checklist (Pressman): interface, local data, independent paths, boundaries, and error handling. Add requirement/use-case coverage and negative/security tests where relevant. Exhaustive testing is usually impossible, so prioritize risk and criticality.
Test scaffolding: a driver calls the unit under test; a stub stands in for a called dependency.06

Project test approach

  • Unit: backend modules and ML-service schema/API behavior.
  • Integration: container smoke test across migrations, ML training/classification, and connected services.
  • System/UAT: black-box user workflows; report describes three participants completing the listed tasks.
  • Security: manual VAPT-style checks mapped to OWASP categories.

Know what is and is not measured

The report records functional test results and UAT task completion. It explicitly says formal coverage was not measured, load/performance baselines were not executed, Flutter UI automation was absent, and quantitative model metrics were not evaluated in that release.

Exam quality: distinguish “functional behavior passed” from “model accuracy/performance is proven.” Do not invent results.

Steps, expected result, actual result, pass/fail.

8 · Descriptive practice questions

Try answering aloud or in short paragraphs. For diagram prompts, draw first from memory, then compare with the earlier pages.

1. Define software engineering. Explain its layered technology and apply it to Infra Monitor.
Include quality focus, process, methods, tools; tie disciplined work to reliability, security, maintainability, and the monitoring problem.
2. Explain why software must evolve even though it does not wear out physically.
Changes in requirements/platforms and defects introduced by change can raise failure risk; legacy systems need controlled maintenance and reengineering.
3. Describe the generic process framework and distinguish framework from umbrella activities.
Communication, planning, modeling, construction, deployment; overlay tracking, risk, QA, configuration management, and reviews.
4. Which process model did the team use? Draw its cycle, describe sprint cadence, and justify the choice.
Agile/Scrum; seven two-week sprints; planning, stand-ups, development/testing, review, retrospective; incremental feedback suits a small team and evolving integration.
5. Compare Scrum/iterative delivery with Waterfall for this project.
Contrast sequential stable-requirement fit and late feedback with short increments, earlier working slices, and ongoing feedback; note Scrum still needs planning and quality checks.
6. Draw and explain the high-level architecture. Why is it a hybrid rather than pure microservices?
Show Flutter ↔ Django; PostgreSQL; VictoriaMetrics; Celery/Redis; FastAPI ML; Alloy; external Gemini/FCM. Explain boundaries and the operational cost of extra services.
7. Draw a component diagram and trace telemetry to an anomaly alert.
Label gateway, monitoring, ML, persistence/alert, and interfaces; trace agent → metrics store → scheduled task → model → callback → record/alert → user.
8. Differentiate architecture, component, sequence, and ER diagrams with project examples.
Runtime/top-level structure; module interfaces; time-ordered interactions; data entities/relationships respectively.
9. Explain verification vs validation and white-box vs black-box testing.
Product right vs right product; internal paths/conditions vs externally visible behavior/requirements. Both are complementary.
10. Propose a compact test strategy for Request Shield or incident handling.
Unit feature extraction/state rules; integration with ML/persistence; system role/threshold workflow; equivalence classes, 500/501 boundary or valid/invalid transitions; trace to requirements.
11. What are a driver and a stub? Why is exhaustive testing impractical?
Driver invokes the unit; stub replaces a dependency. Large input/path spaces make exhaustive enumeration too costly; prioritize risk, boundaries, and independent paths.
12. State two strengths and two limitations of the project test evidence.
Strength examples: functional coverage of reported use cases, integrated smoke test, UAT/security checks. Limitations: no formal coverage/load baseline/automated Flutter UI or quantitative model evaluation (as noted in report).
